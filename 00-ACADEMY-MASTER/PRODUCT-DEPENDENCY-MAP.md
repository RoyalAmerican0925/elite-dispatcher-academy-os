# Elite Dispatcher Academy — Product Dependency Map

This map prevents orphaned lessons, unused tools, untaught assessment items and simulations that demand skills students were never prepared to perform.

## Core instructional dependency

`Occupational outcome → competency → instruction → professional language → worked example → guided practice → student tool → knowledge check → applied scenario → exam → practical → simulation → remediation → competency evidence → later transfer`

Every arrow must be defensible.

## Source dependency

`Claim → claim type → authority/source → verification date → curriculum wording → assessment wording → simulation behavior → update trigger`

Legal/regulatory/date-sensitive claims cannot terminate at an uncited curriculum sentence.

## Professional-language dependency

`Term → precise meaning → contrast/misuse → realistic usage → student use → correction/remediation → later reuse`

A glossary entry alone does not establish fluency.

## Tool dependency

`Workflow problem → student tool → guided use → independent use → practical/simulation reuse`

If a worksheet is never used to make a decision, document evidence or support later work, challenge whether it belongs.

## Assessment dependency

`Taught competency → practice opportunity → scored evidence → scoring rule → remediation → completion status`

No scored surprise content. No major competency disappears without evidence or documented rationale.

## Simulation dependency

`Prior instruction → tools/mental model → scenario input → progressive event → decision → consequence → remediation → competency record`

Simulation cannot become a second lecture or a disguised multiple-choice exam.

## Presentation dependency

`Approved content master → branded template → rendered student/instructor artifact → visual QA → accessibility QA → release package`

Visual production must not silently alter controlled instructional content.

## Technology dependency

`Validated business function → workflow/user requirement → technical capability → minimum architecture → app/integration → cost/security/maintenance → release value`

Do not connect software first and invent a reason for it later.

## Change-control dependency

When a controlled fact or competency changes, inspect all downstream dependencies:
1. manual/lesson;
2. dictionary/terminology;
3. student tool;
4. KC/exam;
5. practical;
6. simulation;
7. instructor/scoring;
8. source/date register;
9. branded/rendered copy;
10. LMS/release package.

A change is not closed until affected downstream artifacts are reconciled.
